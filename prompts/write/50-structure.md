# 문서 구조

1. 표는 여러 항목을 같은 기준으로 나란히 비교할 때 쓰고, 칸에는 낱말이나 구 하나만 넣습니다  
   칸에 서술어가 들어가 문장이 되면 칸 너비에 맞추려고 조사와 어미부터 빠지고 명사만 늘어섭니다  
   파일 경로나 명령어처럼 값 하나가 긴 칸은 문장이 아니므로 그대로 둡니다  
   칸에 문장이 들어가야 한다면 한 줄을 온전히 쓰는 정의 목록(굵은 항목 + 설명)으로 바꿔 설명을 완결된 문장으로 적습니다  
   `table-cell-long`은 30자를 넘는 칸을 검출하지만, 판단 기준은 글자 수가 아니라 칸이 문장인지입니다  
   [`| 정규화 | 원본에서 빈 값과 중복을 뺀다 |` → `- **정규화**: 원본에서 빈 값과 중복을 뺀다`]

2. 한 문단에는 주제 하나만 담고, 주제가 바뀌면 빈 줄을 넣어 문단을 나눕니다  
   `paragraph-cram`은 줄이 네 개를 넘는 문단을 검출하지만, 판단 기준은 줄 수가 아니라 문단에 주제가 하나인지입니다  
   한국어 기술 문서 6,387문단 가운데 98.2%가 4문장 이하였으므로 다섯 줄이 넘는 문단은 드물고, 그런 문단은 여러 주제가 섞였는지 먼저 확인합니다

3. 두 대상을 견주는 짜임은 한 문장 안에 두고 문단으로 나누지 않습니다  
   「A는 …이고, B는 …입니다」처럼 대응하는 두 절은 나란히 놓였을 때 견주는 관계가 드러나므로, 절마다 문단을 나누면 2번 조항을 지키는 대신 그 관계가 사라집니다  
   견주는 두 절은 한 주제를 두 면에서 말하는 것이지 두 주제가 아닙니다  
   [`좋은 쪽은 수요가 이익을 끌어올린다는 점입니다` / `짚어둘 쪽은 가격이 꺾이면 급락한다는 점입니다` → `좋은 쪽은 수요가 이익을 끌어올린다는 점이고, 짚어둘 쪽은 가격이 꺾이면 급락한다는 점입니다`]

4. 「첫째」·「둘째」 같은 열거 표시를 한 문단에 둘 이상 넣지 않고, 항목마다 문단을 나누거나 목록으로 씁니다  
   열거 표시가 한 문단에 몰리면 여러 주제가 한 문단에 들어가, 읽는 사람이 한 주제가 어디서 끝나는지 직접 찾아야 합니다  
   [첫째, 값을 읽는다 둘째, 값을 저장한다 → 목록 항목 두 개로 나눈다]

5. 설정값은 이름만 적지 않고 지금 값을 함께 적습니다  
   이름만 있으면 읽는 사람이 값을 확인하려고 소스를 열어야 합니다  
   밀리초처럼 기계가 쓰는 단위에는 사람이 읽는 단위를 괄호로 붙입니다  
   [`CACHE_TTL_MS`로 정한다 → `CACHE_TTL_MS`는 `60,000`(60초)이다]

6. 읽는 사람이 바꿀 수 있는 값이라면 그 값을 고른 근거도 적습니다  
   값만 있으면 손대도 되는지 알 수 없어 그대로 두게 되고, 근거가 있으면 자기 사정에 맞게 고칠 수 있습니다  
   규격이 정한 포트나 외부 서비스가 요구하는 형식처럼 바깥에서 정해진 값은 근거를 적지 않아도 됩니다  
   [캐시 유지 시간은 `60,000`(60초)이다 → 원본이 1분마다 갱신되므로 캐시 유지 시간은 `60,000`(60초)으로 둔다]

7. 같은 사실을 두 곳에 적지 않습니다  
   두 곳에 적으면 고칠 때 한쪽만 고쳐져 서로 다른 말을 하게 됩니다  
   목차에는 링크와 구조만 두고 규칙 본문을 복제하지 않으며, 한 문서 안에서도 표에 적은 내용을 바로 아래 문장으로 되풀이하지 않습니다  
   [목차에 규칙 본문을 함께 적는다 → 목차에는 링크만 두고 규칙 본문은 한 곳에만 적는다]

8. 파일을 옮기거나 지웠다면 그 파일을 가리키던 링크를 같은 작업 안에서 고칩니다  
   나중으로 미루면 링크가 깨진 채로 남고, 읽는 사람은 그 파일이 사라진 것인지 옮겨진 것인지 알 수 없습니다  
   경로를 추측하지 않고 실제 위치를 확인한 뒤에 적습니다
